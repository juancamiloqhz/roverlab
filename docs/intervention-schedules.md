# Intervention schedules

Ticket 11 adds schedules to the existing session. In layout A, open Mission and choose **Use example schedule** before starting. On Ochre Basin, the example requests Explore more at 01:00, introduces the configured storm at 28 / 24 at 06:00, then requests Conserve energy at the same time. This demonstrates scheduling on the current world. It is not a tuned benchmark or a claim about either controller's performance.

The Mission panel lists future requests, actual request times, event data, and mission application times. Saved inspection and replay show the same evidence. Mission control can inspect a planned storm's location, but the scene and controller continue to use rover observations and memory. A distant storm does not become rover knowledge until detection.

## Time and ordering

`expedition-time-v1` uses the existing 100 ms simulation clock. Schedule times must be nonnegative multiples of 100 ms within the expedition's time budget. Validation rejects unsupported times instead of rounding or delaying them. Event IDs are unique. Requests sort by timestamp and placement, then list order resolves ties within that placement. Mission events carry the complete exclusive mission preferences, including preset definitions and their versions. Storm events carry world position, radius, duration, sensor range, and movement-energy multiplier.

The default placement, `before-choice`, runs after Start at time zero. At later times, code advances the preceding action step, finishes any interaction and action completion, then issues due `before-choice` interventions in list order before the next choice. Those requests coalesce before choosing. A storm affects subsequent movement; it cannot change energy already consumed during the preceding step. Due requests also occur at timeout or battery depletion before the expedition ends. No later requests run after completion.

Mission requests retain their requested time and revision even if they cannot apply yet. Travel reaches the next waypoint; bounded inspection, collection, and waiting finish first. The last pending mission request supersedes earlier ones. These rules also govern manual requests. A manual command can invalidate a pending or held choice without executing it. Mission requests cannot change the expedition's scientific objective or scoring rubric.

Manual requests are captured at the current simulated time and retain their placement relative to action boundaries. `setup` requests run individually before Start at time zero. `after-step` requests run individually after the current step and any choice already issued by that step. A request made just after a new wait starts therefore still waits for that action to finish when reproduced. Successive manual requests retain their individual safe-boundary checks, even when they share a timestamp. Within a placement they follow already issued requests and precede pending requests at that timestamp. Repeated commands that do not change the requested mission do not create duplicate manual entries. A scheduled request for already current preferences remains visible as issued without creating another mission revision.

Pauses, pending inference, inspection, teaching holds, and usage pauses freeze simulated time and scheduled evolution. Playback speed changes how quickly the clock advances, never event timestamps. The existing one-storm-per-expedition rule remains. A scheduled storm reserves that storm; clear pending events before starting to use a manual storm instead. Selecting or clearing a schedule retains requests already captured. Reset clears captured history and restores the schedule supplied when the session was created, which is empty in the normal browser session.

## Session and records

Supply `createExpedition({ interventionSchedule })`, or dispatch `set-intervention-schedule` while ready. Read `getSnapshot().interventions` for the complete current schedule and issued-request history. To reproduce manual events, supply a completed record's `results.interventions.schedule` to a new session with matching starting conditions. Ticket 12 owns the user command for a fresh matched baseline expedition.

Version 11 records retain the initial schedule, schedule selections, each request's clock placement, ordered `intervention-requested` events, each request's manual or scheduled origin, mission revisions, existing mission-application and storm events, and final captured schedule. Import validation checks definitions against actual history and payloads. Replay additionally verifies simulated execution, issues each recorded request once, makes no new inference calls, and leaves the source unchanged. Versions 1 through 10 keep their original event rules; absent schedule metadata remains unavailable. The version 10 fixture was captured from commit `70fb87b6e8b9f8281d9881efb5b2d19b09db3b61` before implementation.

`tests/interventions.test.ts` drives the session through different trajectories, simultaneous events, terminal boundaries, manual reproduction, pauses, playback speeds, safe mission application, malformed imports, and version 10 replay. Its usage-pause case exercises the actual backend and SDK with scripted provider transport. `browser/interventions.spec.ts` covers the example schedule, saved/replayed history, manual requests, fractional-second timestamps, narrow-screen controls, and persistence. Automated verification uses no paid calls.
